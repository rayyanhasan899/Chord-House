# ADR-0023 — Privacy lifecycle and security/accessibility hardening

Status: accepted engineering decision, 2026-11-11 (Phase 17). No new paid provider, public sharing or deployment is selected.

## Decisions

1. Personal export is an authenticated, CSRF/Origin-protected POST with current-password verification and explicit consent. Email verification is not required to export data the account can already read; verified email remains required for deletion under the existing policy. Each action is limited to five attempts per account per 15-minute window, in addition to existing session/IP/email limits. Export is versioned UTF-8 JSON, generated from a coherent owner-scoped snapshot and explicit field allowlists. It excludes credentials, tokens, retry/rate keys, deleted payloads and shared supplier/catalog content. No export file is stored on the server. The security application service uses an ExportSource protocol and SQL repository; JSON conversion remains framework independent.
2. Deletion keeps the existing verified-email/current-password/confirmation guard, adds a clear UI with typed DELETE and a confirmation checkbox, and verifies cascades across all private stores. Shared content and supplier/provenance history remain with account actor links anonymized. No new deletion ledger retaining account identity is added. Individual assessment/practice retry tombstones and reminder dates remain until account deletion. Provider backups and deletion-after-restore handling are explicit deployment gates; no external backup deletion is fabricated.
3. Expired tokens, rate windows and idle/absolute-expired sessions are swept at startup and every 15 minutes while the app runs, with an explicit operator command as well. Local captured mail is purged on expired-code cleanup, new capture and matching account deletion. Codes expire after 30 minutes even before cleanup; stopped servers clean up on restart. SMTP messages cannot be recalled from recipients/providers. Cleanup failures produce redacted events, not private payload logs.
4. Every API response is no-store, preserving existing private labels. Authentication changes remount private views; supported same-origin BroadcastChannel peers reload on a non-sensitive change signal to discard stale private state. No profile or credential is broadcast. Forms carrying account data use POST even if a handler is unavailable. Deletion success survives protected-route redirects. Current browsers are the tested target; backend authorization remains authoritative regardless of tab synchronization.
5. Production rejects HTTP based on the server-validated scheme and uses host-only `__Host-chord_session` Secure/HttpOnly/SameSite=Lax cookies, including matching deletion attributes. Only exact HTTPS CSRF origins are accepted in production; no cross-origin browser API allowance is installed. API docs stay available locally and are disabled publicly in production. Deployment must terminate TLS and trust only the actual proxy IPs. HSTS is scoped to the host without preload or subdomain claims. Next/API responses add framing, content-type and referrer restrictions; microphone remains same-origin. CSP blocks external scripts/objects/frames and production eval, while retaining inline scripts/styles required by the current Next bootstrap. This is an intentional limitation, not a nonce-based strict-CSP claim.
6. Production startup rejects superuser, database/table owner, CREATE-capable, role-member/role-switched and role-admin principals. Migrations use a separate administrative process/credential; the runtime uses explicit application-table grants. Development Compose uses a loopback migration owner and must never be promoted unchanged to production. Real PostgreSQL tests use a separately created limited principal, prove normal writes and reject schema creation. No real user role is provisioned.
7. Request bodies are limited to 8 MiB including streamed bodies. Generic errors and allowlisted logs exclude inputs/secrets. Existing parameterized queries, schema constraints, role checks, per-component grants and browser-local audio are preserved. The limit is per import/request, not a catalog-size cap.
8. WCAG 2.2 AA is the review target: keyboard focus/skip target, current navigation, disclosure/checkbox targets, text alternatives, reduced motion, labels and live feedback are checked through real-browser accessibility trees, axe and journeys. This does not claim an independent accessibility certification or live NVDA/VoiceOver review.

## Dependency exception and limits

The existing lock has nine moderate development-tool audit entries derived from [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249). A patched minimatch override produced a dependency tree rejected by `npm ls`; a clean resolution also failed against the existing React/radix peer tree. Those attempts were restored rather than shipped. No runtime npm finding and no finding in 47 pinned Python packages was observed in this phase's scans. The CI policy accepts only this development-only advisory graph, at low/moderate severity, until **2026-12-11**, and rejects runtime, unknown, severe or expired findings. This is a temporary engineering risk decision; it is not owner approval or a statement that all dependencies are vulnerability-free. Do not lint untrusted third-party configurations while it remains open. Compatible upstream remediation remains required.

The source baseline's registration duplicate status and SMTP eligibility timing can reveal address existence; generic login/reset text and rate limits mitigate but do not establish enumeration resistance. Public deployment must review recovery timing/delivery and operator/provider/backup policies. No hosting/SMTP provider or jurisdictional compliance claim is invented.
