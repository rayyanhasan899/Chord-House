# Frontend foundation — Phase 06

English App Router routes are grouped into public forms/privacy and protected account/onboarding pages. A shared responsive shell supplies working navigation, a skip link, accessible native controls, consistent feedback and light/dark/system tokens. CVA button/input/feedback primitives follow the configured shadcn conventions. No future tool links or nonfunctional buttons are presented as available.

The backend is the authorization boundary. Protected client layouts render no account data until GET /api/v1/me validates the cookie. A missing session redirects to login; network/service failure displays a retry screen instead of pretending the user is signed out. Context generation guards discard stale initial responses after login/logout. Cookies are HttpOnly; CSRF tokens remain in memory. No credentials or session tokens are stored in browser storage. Next rewrites proxy only /api/v1 to the configured server-side CHORD_API_ORIGIN, preserving browser origin, cookies and response headers. Local default is port 8000. Production HTTPS origin settings remain required.

Native constraint validation and server feedback work together. Forms disable their fieldsets until hydration completes and during submission, preventing credential submission before client handlers attach. Failed requests preserve entered values. Code-entry forms avoid putting tokens in URLs. Form messages use alert/status semantics; password change signs out all sessions and returns to login. Optional onboarding preferences have usable defaults; instrument and skill remain essential. Saved preferences can be revisited.

OpenAPI JSON and generated TypeScript declarations live in frontend/src/lib/api. openapi-fetch uses the generated paths; shared HTTP error models document actual identity statuses. `npm run contracts:generate` regenerates both files from the local backend; `npm run contracts:check` fails on drift. Generated files are excluded from formatting so the generator remains deterministic. CHORD_PYTHON can select the Python interpreter in CI. Chord-display preference needed one additive migration (0004), a small API prerequisite for the complete preferences form.

`backend/tests/run_postgres.py --browser` creates an isolated database, runs all backend tests, launches a private API on 8100, builds the frontend for that API and runs Chromium on 3100. Private mail capture and services are removed on completion. Never reuse a personal/production database as CHORD_TEST_DATABASE_URL. Standalone browser smoke mode explicitly skips the account journey without its real mail/API harness; the complete runner and CI backend job run all three tests without skips.

Checks cover registration, incorrect credentials, onboarding, persisted preferences/dark theme, protected redirects, verification, reset, password change, logout, offline recovery, keyboard skip link, mobile/tablet/desktop overflow and automated accessibility on rendered pages. These are Chromium/automated results; manual screen-reader and full cross-browser validation remain Phase 17/18, not unfinished Phase 06 implementation.

Local quick start uses scripts/dev.py: it creates ignored credentials only for a new local database, preserves existing volume credentials, runs migrations and reference seeding, then starts the API and frontend. It leaves an existing frontend process alone. No external deployment or SMTP account was created. Development mail capture is private local data and must remain untracked.
